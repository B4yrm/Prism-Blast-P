### S.eco schema v1 (no effect on the economy yet)

```
S.eco = { v: 1, seed, clock: { acc, hours }, rng: { catch, weather, market, contracts, events, damage: [4 × uint32] },
          mix:  { quay, wh, mRaw: [5 species shares] },  pmix: { facOut, mProd: [5 product shares] },
          q:    { quay, wh, facOut, mRaw, mProd: 0..1 },  flags: {} }
```

`seed` is derived from `S.created`, so the same save always gets the same seed. Mixes start at the reference mix
(GDD §3.1). Quality is 0.8 for stock that existed before eco, and 1 for an empty place. Nothing reads these values yet.
`S.eco.clock` is stored but not advanced: the adapter's clock is still the in-memory T1.1 clock, because `adapter.js`
was not to be changed. Wiring the two together belongs to T1.5.

### Rules (initEco)

| S.eco found | Result | Status |
|---|---|---|
| missing / `null` | new S.eco | `fresh` |
| not a plain object (string, number, boolean, array), or `v` not a positive integer | the old value is kept in `S.ecoBak = { at, reason, value }` (if ≤ 20,000 chars of JSON), and a new S.eco is made | `recovered` (logged as ECOERR) |
| `v` > 1 (made by a newer build) | **left exactly as it is** (same object, nothing written). Eco stays off for the session and `setOn` is refused. | `future` (logged as ECOERR) |
| `v` < 1 | handled by the rule above. `v` < current with a migration step: migrated step by step. Missing step: treated like `future`. | `migrated` |
| `v` = 1 | missing fields filled, bad values repaired field by field, extra keys kept | `ok` / `repaired` |

Reconcile repairs: invalid or negative share vectors and wrong lengths become the reference mix; a sum ≠ 1 is
normalized (proportions kept); an empty place gets the reference mix and quality 1; quality is clamped to 0..1, and
NaN becomes 0.8; the clock is range-checked; an invalid RNG stream is recreated from the seed; flags other than 0/1
become 0; `-0` is stored as `0`. Nothing outside `S.eco` (and `S.ecoBak` on recovery) is ever written.

### 5.1 Boat sync: judgement

The failures are pre-existing flakiness, not caused by T1.2:
- the unchanged base build failed in every full run here (15/17 twice) and in 1 of 4 `start-fleet4` repeats; the eco build
  did no worse (16/17 twice, 4/4 repeats);
- the failing scenario changes from run to run, and every failure is one of the two timing checks
  (`slipTripsInBeforeUnloading`, `curveTripsInTime`). `simulationUnchanged` passed in all 17 scenarios of all 4 full runs;
- in T1.1 (another day, another load on the machine) the same test gave 17/17 on the eco build, so the result depends on the machine;
- the committed result of an earlier build already had a 1.4 s late arrival in this scenario (limit 1.5 s);
- the test's own header says its start-up frames run in real time. The number of arrivals differs from run to run
  (149–157), so it is not deterministic;
- the deterministic tests (workers regression, eco-browser stepped equivalence) show that simulation and drawing are identical.

The check was not loosened and the test was not changed. Because of this, **the boat-sync result is not a
reliable pass/fail signal for later tasks** unless the base build is run next to it on the same machine.
Raw data: `t1.2/boat-sync-eco*.json`, `t1.2/boat-sync-base-run{1,2}.json`, `t1.2/boat-sync-repeat/`.

## 6. Problems found

1. **-0 in stored numbers (fixed in T1.2 code).** The fuzz test found that `-0` passes every range check, but the save
   writes it as `0`, so S.eco would not survive a save and load unchanged. `reconcile` now stores `0`.
2. **A bug in my own fuzz generator (test fixed).** A shared pool array picked up properties from earlier cases.
   This cannot happen with a real save, which always comes from `JSON.parse`.
3. **`save-compare.cjs` reports a failure by design** once the save gains a key. Keep reading its diff list
   (it must contain only `eco`). Changing the test would be a test-tool decision.
4. **`boat-sync` timing checks are flaky on this machine** (§5.1). The base build fails them too (15/17 twice). This is
   a test-stability issue in the existing suite (real-time start-up frames). Fixing it is outside T1.2 and needs a decision.
5. **The existing tests write into committed result files.** For T1.2 they were run from an identical copy of `tests/`
   (verified by sha256), so no committed file was overwritten.

## 7. Remaining risks

- **Stale quality after an old build fills an empty place:** quality 1 (fresh) is kept for stock the old build brought in.
  This is harmless now, because nothing reads quality. When quality matters (T2.5), stock that appears without an eco
  record will need a rule.
- **Old-build play time is not reflected in S.eco:** the clock and the RNG stay where they were. This is fine for T1.2.
  The offline and elapsed-time rules come in T2.6.
- **S.ecoBak stores only the last unreadable value** (≤ 20 KB). A second recovery replaces it.
- **A future schema blocks eco for the session but keeps the data.** A player who rolls back from a newer eco build
  plays this build without eco, which is the intended safe behaviour.
- **Android:** no device or emulator run (same constraint as T1.1, Q10).
